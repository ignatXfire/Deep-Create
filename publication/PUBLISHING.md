# Owner release checklist

This privacy-cleaned revision is prepared locally; preparing it does not update an existing GitHub repository or NotebookLM notebook. Publish only the `DeepCreate` directory contained in the release archive. Do not publish its preparation directory, private audit material, translation caches, local sessions, or the original project history. Read [privacy boundaries](PRIVACY.md) before changing visibility.

1. Read [validation](VALIDATION.md) and [scope](PUBLICATION_SCOPE.md). Keep the research-snapshot warning and known failed checks visible.
2. The owner selected **Apache-2.0** for original project code and documentation. Keep the root `LICENSE`, `NOTICE`, [license scope](../LICENSE-STATUS.md), and [third-party review](../THIRD_PARTY_NOTICES.md). Dependencies retain their own terms; this is not a binary-distribution license clearance.
3. Public attribution is **Ignat**, X **[@ignatXfire](https://x.com/ignatXfire)**. Do not infer a GitHub username or private email from that profile. Use a GitHub-provided no-reply commit address or another deliberately public address. Keep [AUTHORS.md](../AUTHORS.md) and [CITATION.cff](../CITATION.cff).
4. Extract into a fresh directory. If using Git, initialize new history there; do not reuse the original `.git` directory or its branches/tags. Inspect the staged file list before the first commit. Verify author and committer addresses in every reachable commit, not just the newest one. Enable GitHub private email for future web edits and server-side PR merges; a local noreply configuration does not control the email selected by GitHub when creating a merge commit. Recheck metadata after each merge. Replacing an existing remote history requires an explicit owner-approved plan; do not force-push blindly. Replacing a branch tip does not guarantee removal of the old commit from PR references or GitHub caches.
5. Run a fresh secret scan before uploading. Inspect any new media, logs, configuration, and generated files separately. A clean snapshot scan does not cover future edits.
6. The current media refresh contains the approved logo, poster, 60-second research trailer, and unchanged original 39:30 English audio podcast under `assets`. Keep the direct MP4 and M4A links as fallbacks. For a native README video player, upload the reviewed trailer as a GitHub video attachment and put the returned `https://github.com/user-attachments/assets/...` URL on a paragraph by itself; do not substitute a repository/raw URL or fabricate an attachment ID. The trailer is approximately 4.7 MB, below GitHub's 10 MB free-plan video-attachment limit. Keep its research-scope label and the music attribution in `assets/MEDIA_CREDITS.md`. Do not replace the podcast bytes; add its X post link when the owner provides the actual URL. The original podcast is about 76 MB: retain it through Git rather than the browser's 25 MiB file uploader; it is below GitHub's 100 MiB Git-file limit. NotebookLM is a separate copy: the owner reports that its sources have been refreshed, but actual source contents and sharing permissions require their own check. Do not upload private production workspaces, logs, account data or filesystem inventories. Review future recordings for exposed terminals, account names, tokens, notifications, paths and hardware information.
7. Once the actual public GitHub repository exists, enable **Private vulnerability reporting** in repository settings and check that `Security -> Advisories -> Report a vulnerability` is available. [SECURITY.md](../SECURITY.md) describes this selected channel, but creating that file does not enable GitHub's feature. Never request credentials or exploit details in a public issue. The owner's X account is not a guaranteed private or monitored channel.
8. Use the actual repository URL in announcements and citation metadata only after creating it. The original owner is not committing to ongoing development, issue response, or merging contributions; maintained forks are welcome under [CONTRIBUTING.md](../CONTRIBUTING.md). No repository access is automatically granted.
9. Preserve the owner-approved About description and use relevant topics rather than popularity claims. Topics can be edited with the gear beside About; they classify the project, not its maturity. Configure the separate social preview under repository Settings before announcing a public link. Keep personal tips in [SUPPORT.md](../SUPPORT.md), explicitly separate from project funding and maintenance obligations; publish only owner-confirmed receiving addresses and exact networks.

Publishing source does not itself grant access to the owner's computer. Exposed credentials, private operational data, or vulnerable software running with valuable permissions are separate risks. The packaging checks reduce accidental disclosure; they do not establish production security or eliminate all publication risk.
