# Deep Create: checking the risks and hidden places of a new direction

**Date:** 2026-09-04  
**Status:** architectural analysis of owner's responses; This is not yet proof of a working protection.  
**Goal:** Maintain Deep Create's desired autonomy without turning a convenient switch, model, or self-change into an uncontrollable source of power.

## 1. Main conclusion

The new direction is stronger than the previous one: Deep Create should be a stand-alone application, and not a tab inside Hermes. This allows you to separate your storage, security foundation, processes, updates, and control screen from the constraints of someone else's project.

But several wishes cannot be transferred literally into the program:

1. The “on” switch is not permission to perform any action. He chooses a pre-approved order of independence.
2. Wide memory search does not mean transferring all memory to each model.
3. Self-improvement cannot overwrite the security foundation that issues rights and stops the system.
4. The “don’t delete anything” requirement does not mean storing keys and passwords in clear text or endlessly filling up the system disk.
5. Random folder names are not a security feature. They are only valid as additional isolation for temporary copies.
6. After a sudden power outage, the system will no longer have time to “see the red flag.” The necessary information must be saved until failure, at each important transition.
7. A hard stop cannot cancel an email that has already been sent or a payment that has already been made. It must immediately prohibit new actions and separately clarify the outcome of those already started.

This is not a rejection of the user's philosophy. On the contrary, these are boundaries that allow autonomy to remain real and not rest on the model’s promise to behave correctly.

## 2. Automatic switch

### What the owner wants

The owner enables or disables the system's right to offer deep mode, select working directories, continue working, and, in predetermined cases, act without constant questions.

### How it should work

The switch selects one signed rule set. The set of rules itself contains:

- what types of actions are allowed;
- with which recipients and services;
- what types of data can be transmitted;
- marginal cost and frequency;
- validity period;
- reasons for mandatory contact with a person;
- list of prohibited actions;
- rules version number.

The model can suggest a different set or explain a choice, but cannot itself expand the current set. Changing the switch creates an owner event, a new version of the rules, and a beacon. Old performers do not automatically receive new rights.

### Why one switch is not enough

If “enabled” simply means “the models can be solved by themselves,” then it is impossible to prove where the authority ends. Two models will be able to understand the same switch differently. Therefore, the convenient button remains on the screen, but under it there is always an accurate machine description.

## 3. Independent external actions

For constant communication with clients, you need not a general refusal of confirmations, but a **limited order**. It pre-sets acceptable recipients, types of messages, working hours, frequency, prohibited topics, types of personal data and reasons for contacting the owner.

Contacting a person is mandatory if at least one of the following occurs:

- a new recipient has appeared;
- payment, contract or account information has changed;
- the amount above the limit set by the owner is affected;
- the communication creates a legal or public obligation;
- you need to transfer a secret, key or sensitive personal information;
- the interlocutor asks to go beyond the boundaries of the assignment;
- models and inspectors do not agree with the risk assessment;
- it is unclear whether the previous action was completed.

Evaluating the model can add a reason to contact a person, but cannot cancel the listed machine prohibitions.

## 4. Permissions and separate confirmation path

Requesting permission should not go through the model's work conversation like regular text. A separate trusted path is needed:

1. The performer creates an action proposal.
2. The control layer independently collects a precise description of the action, recipient, data, price, files affected, and expected consequence.
3. The screen shows the permission card in the list and in the main work column.
4. The owner confirms, changes the scope, sets a deadline, or refuses.
5. The program turns the answer into an accurate record of rights and shows the owner the final interpretation.
6. Only a trusted interface handler creates a valid right. Text from a model, file, site or extension cannot create such a right.

The owner's original wording is retained as evidence. The machine interpretation is kept nearby, but does not replace the original wording. If free text allows two interpretations, the action does not begin until the owner sees and confirms one of them.

### Permit period

The term is stored not only as a number on the screen. The start time, end time, hours used, authorization generation number, and status: pending, active, used, expired, revoked, or needs reconciliation are recorded.

After the computer sleeps or restarts, the permission is not renewed. If the system clock has been set back or its accuracy is questionable, the authorization is considered invalid until reconciliation. Perpetual permission should be a separate visible type of assignment, not an absence of date.

### Review

Revocation should be simpler than issuing rights. Therefore, it is recommended not to require an additional checkbox to terminate the permission: clicking immediately revokes the right, and a possible “return” is considered a new issue and again requires confirmation. This is safer than delaying the review with a second window.

## 5. Two types of stops

### Hard stop

The hard stop is performed by a separate local watchdog process, not by the model or the person doing the main work. He:

1. increases the generation number of powers;
2. closes the issuance of new rights;
3. blocks the intermediary of file, network and external actions;
4. completes the tree of local processes of the main work;
5. marks already started external actions as requiring reconciliation;
6. Saves minimal emergency recording.

The model cannot defer, cancel, or override this command. However, the screen must honestly warn: a hard stop does not return external consequences that have already occurred.

### Soft stop

A soft stop first prohibits new units of work from starting, then asks current units to reach a safe point, save the results, and prepare to continue. The owner's text becomes a stopping condition. If the deadline established by measurements has expired, a ban on late fixation and, if necessary, hard termination are applied.

Five or six minutes can be used as a window to cancel a soft stop plan that has not yet been started. This is not “taking back what has already been done.” Resuming after a permanent stop creates a new generation of permissions and re-checks files, sources, and pending actions.

## 6. Sudden shutdown and continuation

Protection is not based on trying to save everything when turned off, but on permanently recording the state:

- intention is preserved before action;
- after each accepted transition, the new state and beacon are saved as one indivisible record;
- large materials are first written to a temporary object, checked and only then become active;
- the external action receives one stable key so that repetition does not create a second result;
- working performers regularly maintain a sufficient continuation point;
- after startup, the system first restores and verifies, and does not immediately continue.

The owner's command to "continue" indicates permission to begin reconciliation. It should not automatically return old rights or repeat an unknown external action.

Mandatory tests: force the process to end and turn off the power at each important transition, then prove one of two states - completely old or completely new. A mixed state is considered an error.

## 7. Memory, skills and broad independence

The desire not to limit Deep Create in knowledge is realized by two different boundaries:

1. **Local Search** can search a wide pre-approved set of sources.
2. **A specific performer** receives only the work selection needed for his unit of work.

Otherwise, one connected model or malicious extension will see the entire personal archive. Broad searches remain possible, but disclosure of data to each artist remains minimal.

Past work can only be transformed into new skills, rules, and solutions as derivative proposals. Each such sentence stores the origin, benefit examples, negative cases, tests and version number. Search index and condensed knowledge help to find information, but do not have the power to declare a fact true or give authority.

## 8. Self-development

The independent inclusion of improvements chosen by the owner is not accepted in its entirety, but in two levels.

### Area where self-activation is acceptable

The system can itself enable a change if it is simultaneously proven that it:

- does not change the protective base;
- does not expand access to files, network, memory, secrets and external actions;
- does not change the rules for stopping, logging, checking and returning;
- completely reversible;
- passed repetition of old tasks, hidden set of tests, hostile checks and limited observation;
- has a predetermined measurable improvement without deterioration of mandatory indicators;
- is enabled by a separate control process, and not by the author of the change.

### Area where self-start is prohibited

Without the owner you cannot change:

- root of trust and authority number;
- rules for issuing and revoking permits;
- mediator of external actions;
- processing of keys and personal data;
- mandatory beacons and “completed” conditions;
- the mechanism of testing and approval of the new version;
- possibility of a hard stop;
- the boundaries defining this prohibited area.

This does not make development manual. Models can independently create, compare, correct and test many options. The manual boundary remains only around the mechanism that defines their power.

## 9. Why random names are not protection

Changing folder names may make primitive substitution more difficult, but it also breaks links, recovery, version comparison, and explainability. An attacker who already has access to the file system will be able to see the new name.

Correct solution:

- give each main job and unit of work a random, unchangeable internal number;
- associate each material with a verifiable content fingerprint;
- store a signed list of expected files and versions;
- check for a real open Windows object, not a path string;
- give each performer a separate working copy;
- include changes in their entirety only after verification;
- use random temporary names only as an additional measure against coincidences.

## 10. Indefinite saving and lack of space

The owner's requirement is interpreted as follows: **semantic evidence and initial data of the decision made are not automatically deleted**. In this case:

- keys and passwords are stored in a separate secure storage, and not in a general journal;
- identical copies can be replaced by one verified copy with links;
- search pointers, temporary assemblies and recoverable intermediate data can be recreated;
- old materials are compressed and transferred to encrypted cold storage;
- integrity checks are carried out for each media;
- the system estimates the filling speed in advance, rather than waiting for the last megabyte.

A small emergency reserve is reserved on the disk. When inventory is low, new hard work does not begin. When there is a critical balance, all main work is paused, external actions are blocked, and the screen shows which disk is full, what is taking up space, what is allowed to be transferred, and how much needs to be freed. After freeing up space, the database is checked and only then is it allowed to continue.

## 11. Setting up through normal conversation

A regular chat for a new application can accept commands like “add a connection”, “work in this folder” or “set everything up yourself”. But the model only creates a **proposal for changing settings**. Next:

1. the precise parser turns the proposal into changing specific fields;
2. the protective layer checks the admissibility and required rights;
3. The screen shows the difference between the previous and new state;
4. the owner confirms the sensitive change;
5. The database and log are updated with one indivisible record.

The connection key is entered through a secure field and saved by the operating system. The model receives the designation of the secret, but not its value. The plug-in module substitutes the secret only at the time of access and does not write it to the log.

## 12. Beacons of a new direction

Each beacon contains the main work number, work unit number, state version number, event source, active rule, time, observed result and a link to the proof. The full text of sensitive data is not included in the beacon.

## 13. Hidden scenarios that must be experienced

| What can happen | Correct reaction | Sign of failure |
|---|---|---|
| The model writes “user allowed” | The right does not appear without a trusted interface event | Model text creates the right |
| Permission expires during validity | The new commit is blocked; irreversible external launch is verified | Late result is accepted as normal |
| Windows clock set back | Permits are frozen until time check | The old resolution is getting longer |
| Computer loses power while recording | After startup, the old or new version is completely restored | Base and magazine diverge |
| Computer loses power after sending but before responding | The outcome is marked unknown and found out using a stable key | Sending is repeated blindly |
| Hard stop pressed when the model is frozen | Separate guard process closes middlemen and process tree | The model can ignore the stop |
| A malicious extension requests the entire archive | Receives a refusal or minimal selection | Inherits the rights of the parent |
| The imported conversation contains a hidden command | The team remains untrusted data | She changes settings or rights |
| The new model has the same name in another service | Considered a separate connection | She gets someone else's story of reliability |
| Temporary model quota has ended | The route is cooling, the work is waiting or changing the connection safely | All main work falls |
| Self-Improvement Changes Self-Trials | External immutable reviewer rejects version | The author of the improvement himself declares success |
| Self-improvement fills disk with options | Separate limit stops candidate creation | The main magazine breaks down |
| Old copy restored | All previous rights are invalid, the system is limited | Canceled permission comes back to life |
| Two branches change one file | Changes are made in separate copies and are checked after merging | Last entry wins |
| The user accidentally selected soft stop | Short cancellation available before her plan starts | Cancel returns an action that has already been completed |
| The user accidentally selected a hard stop | The work is restored only from the last whole point and new rights | Interface promises full refund |
| The screen is out of date | The command with the outdated version is rejected and the screen is updated | Old screen revokes new right |
| Disk almost full | Work is paused until critical balance | Write error detected after action |
| Reviewers use one source of error | The result is considered a replay and not an independent verification | Same opinion is considered evidence |
| Search finds no new information | A predetermined sufficiency condition is triggered | Research lasts forever |

## 14. Fixed rules

The following rules should be below models, skills and self-modifying parts:

1. Only the owner's entrusted event or a pre-issued precise right allows action.
2. No performer expands his own rights.
3. Unknown execution path is prohibited.
4. An unknown external outcome is not considered a repeatable failure.
5. Revocation of the right immediately prohibits late fixation.
6. The status “completed” requires proof and acceptance by the owner according to the selected rule.
7. Secrets do not go into the general log and model requests.
8. Restoring an old copy does not restore privileges.
9. Self-improvement does not change the rules of one's own admission.
10. Lack of space or ability to record a mandatory beacon blocks the protected action.

## 15. Bases verified against external primary materials

- [SQLite: Indivisible Commit and Power Failure Recovery](https://www.sqlite.org/atomiccommit.html) - Reaffirms the need to record pre-failure transitions and recover incomplete writes rather than rely on the shutdown handler.
- [SQLite: Pre-Write Log](https://www.sqlite.org/wal.html) - Shows the benefits of parallel reads and writes, but also warns about log growth and the need to manage control transfers.
- [Microsoft: Windows redirect points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points) and [open real file object](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea) - confirm that text checking for the start of the path is not enough.
- [NIST: Generative AI Risk Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) - links governance, data provenance, pre-enablement testing, and incident management into one lifecycle.
- [Secure Updates Specification](https://theupdateframework.github.io/specification/latest/) - shows the need for a trusted root, continuous version sequence, and no reversion to an older trusted version.

## 16. Fair boundary of this document

The document defines mandatory boundaries and tests, but does not select the program language, interface library, exact format of tables and numerical deadlines. These decisions must be made after measurements and prototypes. None of the defense mechanisms described here are considered to be implemented yet.
